# N8N como enviar Resposta no WhatsApp | Curso de Agentes (Aula 3)

> Aula prática que fecha o loop do bot: pega a resposta gerada pela OpenAI e devolve ela ao WhatsApp que mandou a mensagem, usando um node HTTP Request configurado para Evolution API ou Avisa App.

**Canal:** [Rhavi Criador Digital](https://criador.digital)  · **Duracao:** 00:22:19 · **Publicado:** 2025-03-30 · [Assistir](https://www.youtube.com/watch?v=NirF5cRTEA8)

## 1. Tese central

O que faltava no fluxo era o passo de "responder de volta". Depois que a mensagem chega no Webhook, passa pelo parser, pela normalização (nome, número, mensagem, grupo) e por um IF que separa grupo de não-grupo, o texto do usuário vai para a OpenAI, e a resposta da IA precisa ser enviada de volta ao número que escreveu. Esse envio é feito por um node HTTP Request fazendo um POST para o endpoint de envio de texto da API de WhatsApp (Evolution API ou Avisa App). O vídeo ensina a montar esse node nas duas APIs para deixar o aluno "100% independente" e com opção de backup.

## 2. Frameworks e modelos mentais

> Cada framework recebe nome, explicacao, quando aplicar e citacao verbatim com timestamp.

### 2.1 Node HTTP Request como "boca de saída" do bot

**O que e:** Todo envio de mensagem ao WhatsApp no n8n (quando não se usa um node nativo da API) é uma requisição HTTP POST para a URL de envio da API, carregando número de destino e texto no corpo, mais autenticação no header.

**Como funciona:**
1. Adiciona o node HTTP Request depois do node da OpenAI e renomeia curto (ex.: `envio`, `envio_avisa`, `envio_evo`).
2. Método `POST`, porque está mandando dados para uma API.
3. URL do endpoint de envio de texto (da documentação da API).
4. Header com `Content-Type: application/json` e a autenticação.
5. Body em JSON com o parâmetro de número e o parâmetro de texto (a resposta da IA).
6. Test Step: código 200 e `success: true` significam que funcionou.

**Quando aplicar:** Sempre que o bot precisa responder ativamente no WhatsApp (resposta da IA, confirmações, notificações).

**Quando NAO aplicar:** Quando a API tiver node nativo pronto no n8n e você não precisar da flexibilidade do HTTP genérico (o vídeo prefere o HTTP genérico justamente para ensinar independência).

> "E aí agora a gente precisa mandar essa mensagem para o WhatsApp que enviou o Oi, né? Então, como que a gente vai fazer isso? A gente vai clicar aqui e vai selecionar HTTP request. Que vai ser uma requisição de API."
> — [00:02:45]

### 2.2 Autenticação por Credential genérica (Header Auth) em vez de chave inline

**O que e:** Em vez de digitar a chave de API direto no header do node, cria-se uma Generic Credential do tipo Header Auth. Assim a chave fica fora do JSON do fluxo.

**Como funciona:**
1. No campo Authentication do HTTP Request, escolher Generic Credential Type e Header Auth.
2. Dar um nome à credential (ex.: `Evolution`, `Evo 2`, `Avisa App`).
3. Preencher Name e Value conforme a API (ver Seção 3).
4. Selecionar essa credential no node; o parâmetro de auth some do header do node.

**Quando aplicar:** Sempre que for compartilhar ou exportar o fluxo (evita vazar a chave no JSON exportado).

**Quando NAO aplicar:** Teste rápido e privado, onde colocar a chave direto no header resolve (mas o autor recomenda a credential como boa prática).

> "Mas se você compartilhar o seu fluxo com alguém e esquecer de tirar a sua chave de API, o seu fluxo, o seu JSON, ele vai com esses valores aqui. Agora, se você selecionar uma autenticação e criar a sua própria autenticação..."

## 4. Heuristicas e regras

- **Nomes curtos nos nodes** — o autor renomeia o node de envio para `envio`, depois `envio_avisa` e `envio_evo`, para diferenciar as APIs quando o fluxo tiver muitos módulos de HTTP. [00:03:11]
- **Content-Type sem aspas e sem dois-pontos** — a "pegadinha" que custou pra ele entender: no Name do header escreve só `Content-Type`, sem os dois-pontos, e o Value é `application/json`. [00:06:33]
- **Vírgula por vírgula** — os nomes dos parâmetros do body têm que ser exatamente iguais aos da documentação; um caractere errado gera erro e o n8n não aponta onde está. [00:09:04]
- **Número já normalizado sem @** — por isso a normalização de aulas anteriores trata o número tirando o arroba, senão o envio falha. [00:08:00]
- **Credential em vez de chave inline** — ao compartilhar o fluxo, use uma credential de autenticação para a chave não ir junto no JSON exportado. [00:13:30]
- **Tenha uma API de backup** — em produção, se a Evolution cair, ter um módulo de envio de outra API (Avisa App) pronto e a base URL como variável na normalização acelera a troca. [00:16:45]
- **Content-Type por via das dúvidas** — o n8n às vezes já manda o Content-Type sozinho, mas o autor adiciona mesmo assim para garantir acerto de primeira. [00:15:15]

## 7. Contra-argumentos e nuances

- A Avisa App e a Evolution são "muito similares, mas têm as suas particularidades": os nomes dos parâmetros e o tipo de autenticação mudam entre elas (número/mensagem + Bearer na Avisa; number/text + apikey na Evolution). [00:10:08]
- O n8n pode já enviar o Content-Type sozinho, então adicioná-lo manualmente pode ser redundante, mas o autor mantém para não arriscar erro. [00:15:23]
- A base URL só precisa virar variável na normalização para a Evolution (cada usuário instala na própria VPS/domínio); para a Avisa App não precisa, porque a URL é fixa. [00:17:33]

## 8. Aplicacao no nosso contexto

> Esta secao conecta o conhecimento absorvido com o projeto do bot BaseX no WhatsApp (grupos de alunos; stack Evolution API + n8n + Claude; atende dúvidas e faz gestão).

**O que isso muda na nossa operacao:**
Esta aula entrega exatamente a peça de saída do nosso bot: como o n8n devolve a resposta ao WhatsApp depois que o Claude gera o texto. No nosso stack (Evolution API), o node de envio é um HTTP Request com método POST para `{baseURL}/message/sendText/{instance}`, onde `baseURL` é o domínio da nossa VPS Evolution e `instance` é o nome exato da instância conectada. O corpo vai em JSON com `number` (o destino) e `text` (a resposta do Claude). A autenticação da Evolution é do tipo API Key simples: criar uma Generic Credential Header Auth com Name `apikey` e Value = a chave, sem prefixo Bearer (diferente da Avisa App, que usa `Authorization: Bearer <token>`).

Ponto importante para o bot de grupos: o vídeo mostra o fluxo do ramo "não é grupo" (responde direto no privado do número). Para responder dentro de um grupo de alunos, o destino no campo `number` não é o telefone individual e sim o JID do grupo (o identificador que termina em `@g.us` no payload do webhook). Como no nosso caso a resposta precisa cair no grupo, o campo de destino deve ser mapeado a partir do identificador do grupo capturado na normalização, não do número pessoal. A aula não cobre esse detalhe (só trata o ramo privado), então isso fica como ajuste nosso na hora de mapear o destino.

**Gotchas para o nosso bot:**
- Nomes dos parâmetros do body têm que bater exatamente (`number`, `text` na Evolution); erro de digitação quebra sem mensagem clara.
- O destino precisa estar normalizado (sem `@`, no formato que a Evolution espera); para grupo, usar o JID do grupo.
- Usar credential de autenticação (não chave inline) para não vazar a chave da Evolution ao exportar/versionar o fluxo.
- Guardar a base URL da Evolution como variável na normalização, facilitando backup se a API cair.

**Acao concreta sugerida:**
- [ ] No fluxo do bot BaseX, confirmar o node de envio Evolution: POST em `{baseURL}/message/sendText/{instance}` com credential Header Auth `apikey`.
- [ ] Mapear o campo `number` do envio para o JID do grupo de alunos (`...@g.us`) quando a resposta for para grupo, não para o número pessoal.
- [ ] Guardar a base URL da Evolution como variável na normalização para permitir troca rápida de API.
- [ ] Validar retorno 200 / success e tratar erro de parâmetro (checar nomes exatos do body).

## 11. Glossario (se aplicavel)

| Termo | Significado |
|-------|-------------|
| HTTP Request | Node do n8n que faz uma requisição HTTP genérica (aqui, POST para enviar mensagem) |
| Evolution API | API self-hosted de WhatsApp (rodando em VPS/domínio próprio); auth por `apikey` |
| Avisa App | API paga de WhatsApp; auth por `Authorization: Bearer <token>` |
| Instância | Conexão nomeada de um número de WhatsApp dentro da Evolution |
| Base URL | Endereço raiz da API (na Evolution, o domínio da sua VPS) |
| Header / cabeçalho | Metadados da requisição (Content-Type, autenticação) |
| Body | Corpo da requisição em JSON com número de destino e texto |
| Bearer token | Esquema de auth onde o valor é `Bearer ` + a chave |
| Code 200 | Status HTTP de sucesso |
| `\n` | Quebra de linha (enter) no texto |
| Import cURL | Recurso do n8n que monta o node a partir de um comando cURL colado |
| Generic Credential (Header Auth) | Credential do n8n que guarda a chave fora do JSON do fluxo |
