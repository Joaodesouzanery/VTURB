# Filtrar mensagens e Normalizar os Dados (Setar Variáveis) | Curso de N8N para WhatsApp (Aula 5)

> Aula prática de n8n que ensina a normalizar o payload da Evolution API (push name, número, mensagem, participante) e a filtrar mensagens de grupo x privadas usando um nó IF, exatamente o que o bot BaseX precisa para atuar só nos grupos certos.

## 1. Tese central

Para transformar um fluxo n8n em chatbot conversacional confiável, primeiro é preciso padronizar (setar variáveis) os dados que chegam do WhatsApp e filtrar o que não deve ser processado. O autor migra o projeto da Avisa API para a Evolution API (mais endpoints, mais versatilidade) e mostra como identificar se a mensagem veio de grupo ou privada, já que a Evolution não entrega um campo booleano de grupo pronto.

## 2. Frameworks e modelos mentais

> Cada framework recebe nome, explicacao, quando aplicar e citacao verbatim com timestamp.

### 2.1 Detecção de grupo pela presença do campo `participant`

**O que e:** Como a Evolution API não expõe um parâmetro `isGroup` true/false, a origem grupo x privado é inferida pela existência (ou não) do campo `participant` no payload.

**Como funciona:**
1. Setar uma variável `participant` puxando o campo `participant` do body da Evolution.
2. Colocar um nó IF com a condição `participant` -> operador "exists" (existe / stream exists).
3. Se existe: é grupo -> ramo true -> não faz nada (ignora).
4. Se não existe (undefined): é mensagem privada -> ramo false -> segue o fluxo do bot.

**Quando aplicar:** Sempre que o bot roda em cima da Evolution API e precisa tratar (ou ignorar) mensagens de grupo.

**Quando NAO aplicar:** Na Avisa API, que já traz o parâmetro próprio de grupo. O autor observa que a Avisa "não tem esse parâmetro isGroupTrueOrFalse" no sentido de que a Evolution é quem não tem, então na Evolution usa-se o participant.

> "No caso da Evolution, ela não tem esse parâmetro isGroupTrueOrFalse. Então, aqui eu preciso de pensar de outra forma. E para isso, eu quero entender como que chega uma mensagem de grupo."
> — [00:03:08]

> "Se o participante existir, significa que é um grupo."
> — [00:06:19]

### 2.2 Normalização de payload (Set / setar variáveis)

**O que e:** Reduzir o payload cru da Evolution a um conjunto limpo de variáveis reutilizáveis no resto do fluxo: nome, número, mensagem, participante.

**Como funciona:**
1. `push name` -> puxa o campo `pushName` (nome de exibição do contato).
2. `número` -> vem do `remoteJid`; aplica `.split` para remover o mais, o arroba e o `whatsapp.net`, sobrando só o número limpo.
3. `mensagem` -> caminho `body` > `data` > `message` > `conversation`.
4. `participant` -> campo `participant` (só existe em grupo).

**Quando aplicar:** Logo no início do fluxo, antes de qualquer lógica de banco ou IA, para trabalhar com dados "clean" na frente.

**Quando NAO aplicar:** Não aplicável quando o payload já chega normalizado por um passo anterior.

> "Eu consigo o número sem o mais, sem o arroba, o whatsapp.net e tudo mais. Eu consigo só o número. Porque é isso que eu quero também para poder reutilizá-la na frente de maneira mais clean."

## 8. Aplicacao no nosso contexto

> Esta secao conecta o conhecimento absorvido com o projeto do bot BaseX (WhatsApp em grupos de alunos; stack Evolution API + n8n + Claude; funções de tirar dúvidas + gestão).

**O que isso muda na nossa operacao:**
Esta aula é diretamente o coração do roteamento do bot BaseX. O bot vive em grupos de alunos, então a decisão "esta mensagem é de grupo e de qual grupo" define se ele responde e como. A aula ensina o mecanismo exato:

- **Detectar grupo x privado na Evolution:** presença do campo `participant` no payload. Se `participant` existe -> é grupo. No bot BaseX a lógica se inverte em relação à aula: em vez de ignorar grupo, nós queremos justamente atuar no grupo, então o ramo "participant exists = true" é o que segue o fluxo.
- **Filtrar por GRUPO específico (origem):** o `remoteJid` do grupo é o identificador do grupo (o JID de grupo termina em `@g.us`, distinto do privado `@s.whatsapp.net`). Setando o `remoteJid` como variável e comparando com uma allowlist de JIDs dos grupos de alunos, o bot atua só nos grupos certos e ignora qualquer outro grupo. O `participant` (quem falou dentro do grupo) vira o identificador do aluno individual, útil para gestão e para saber de quem é a dúvida.
- **Normalizar variáveis do aluno:** `pushName` (nome do aluno), `remoteJid` do grupo (qual turma/grupo), `participant` (qual aluno falou), `conversation` (texto da dúvida). Esse conjunto limpo é o que a gente passa para o Claude decidir se é dúvida a responder ou item de gestão.
- **Padrão de identidade:** normalizar o número do `participant` (mesma ideia de split + +55) permite casar o aluno com o banco (Airtable/Notion) para respostas personalizadas e histórico.

**Acao concreta sugerida:**
- [ ] No fluxo do bot BaseX, criar nó Set com: `pushName`, `groupJid` (do `remoteJid`), `sender` (do `participant`), `text` (de `body.data.message.conversation`).
- [ ] Adicionar nó IF `participant exists`; ramo true (grupo) segue, ramo false (privado) trata separado ou ignora.
- [ ] Adicionar um segundo filtro: comparar `groupJid` contra uma allowlist de JIDs dos grupos de alunos (só atua nos grupos certos).
- [ ] Extrair e normalizar o número do `participant` (split + prefixo país) para casar com o cadastro do aluno no banco.
- [ ] Rodar test step com mensagem real de um grupo de aluno para confirmar os campos antes de ligar a lógica de IA.
