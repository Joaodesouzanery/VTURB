# AULA 4: Agentes N8N no WhatsApp | Set Variables do Jeito Certo

> Como normalizar o payload que chega da API de WhatsApp num node Set (Setar Variáveis) do n8n, deixando o fluxo base de atendimento organizado, tipado e fácil de manter.

**Canal:** [Rhavi Criador Digital](https://criador.digital)  · **Duracao:** 00:14:18 · **Publicado:** 2026-05-18 · [Assistir](https://www.youtube.com/watch?v=_lwx9UNrkgg)

## 1. Tese central

Antes de qualquer lógica de atendimento (filtros, atendimento humano, agrupamento de mensagens), você deve normalizar o payload bruto que chega do webhook da API de WhatsApp num node Set único, chamado "Setar Variáveis". Como cada API (Evolution, Avisa API, etc.) entrega os dados num formato diferente, esse node de normalização vira a camada de tradução: você extrai origem, grupo, id, tipo, timestamp, conteúdo e variáveis fixas da API para nomes padronizados, e o resto do fluxo passa a depender só desses nomes, não do formato cru de cada provedor.

## 2. Frameworks e modelos mentais

> Cada framework recebe nome, explicacao, quando aplicar e citacao verbatim com timestamp.

### 2.1 Normalização via node Set único ("Setar Variáveis")

**O que e:** um node Set (Set Variables) posicionado logo após o webhook que traduz o payload cru da API para um conjunto padronizado de variáveis do fluxo.

**Como funciona:**
1. Recebe o payload do webhook (que muda de formato por API)
2. Cria variáveis com nomes próprios (origem, grupo, id, tipo, timestamp, conteúdo, token, timeouts)
3. Referencia sempre o nó de origem via `item.json` do node parse
4. O restante do fluxo consome só essas variáveis normalizadas

**Quando aplicar:** sempre que integrar uma API de WhatsApp (ou qualquer webhook de formato variável) antes de filtros e lógica de atendimento.

**Quando NAO aplicar:** o vídeo não define contraindicação. Não aplicável — o autor trata a normalização como boa prática universal desse fluxo.

> "Da última vez, a gente já começou a setar as variáveis, que também eu chamo de normalização, tá? A gente normaliza os dados. Por quê? Eles vêm, cada vez que a gente usa uma API diferente, eles vêm de uma forma diferente aqui."
> — [00:00:05]

### 2.2 Multi-webhook para backup entre APIs

**O que e:** manter, em separado, um node Set de normalização pronto para cada API (um para Evolution, um para Avisa API), de modo que se um provedor cair você troca para o backup sem reescrever o fluxo.

**Como funciona:**
1. Duplica o webhook/node Set e deixa a cópia desativada
2. Um Set normaliza no formato da Evolution, outro no formato da Avisa API
3. O conceito de normalização é o mesmo; muda só o mapeamento de campos por API
4. Se a API principal cair, ativa o backup

**Quando aplicar:** operações que dependem de continuidade de atendimento e não podem ficar reféns de um único provedor.

**Quando NAO aplicar:** Não aplicável — o autor apresenta apenas como boa prática preventiva, sem contraindicação.

> "A gente pode preparar vários webhooks, um que vai estar na Evolution, outro que vai estar na Visa API, para se caso, por exemplo, a Evolution cair, a gente tem a Visa API prontinha para um backup."
> — [00:00:24]

## 4. Heuristicas e regras

Regras-de-bolso, atalhos mentais, principios que o autor enfatiza:

- **Sempre referenciar o nó de origem** — escreva `item.json` apontando para o node parse; se você não referencia o nó certo, o campo fica vermelho e, ao inserir um nó intermediário no futuro, o fluxo quebra sem você saber onde. [00:04:41]
- **Verde = referência OK, vermelho = referência quebrada** — o n8n colore os campos; use a cor como validação visual imediata de que a referência está sã. [00:08:52]
- **Corrigir o tipo do campo após transformar** — ao virar `isFromMe` (booleano) em incoming/outcoming (string), troque manualmente o tipo de booleano para string, senão o step falha. [00:07:17]
- **Agrupar por prefixo com ponto** — `user.` para dados do usuário, `message.` para dados da mensagem; deixa o schema organizado (totalmente opcional). [00:07:38]
- **Ordem de organização das variáveis** — do usuário no início, mensagem no meio, as modificáveis manualmente (timeout, atendimento) no final, por costume, para achar rápido. [00:13:33]
- **Centralizar variáveis mutáveis no Set** — qualquer valor que você precise mudar e que afete todo o fluxo mora no node Setar Variáveis; você muda num lugar só, não caça no meio de um fluxo gigante. [00:13:44]
- **Documentar com Sticky Note** — colocar um Note colorido titulando cada etapa ("Setar Variáveis") para reconhecer o fluxo de relance no futuro. [00:01:06]

## 6. Exemplos praticos mencionados

Casos reais, numeros, historias que o autor compartilha:

### Exemplo 1: Áudio chega como binary/arquivo
Ao mandar um áudio de teste ("Oi, testando o áudio") e abrir o webhook, aparece uma terceira aba além de table/json/schema: `binary`. Isso mostra que o áudio chega em modo arquivo, e o tipo real vem em `MediaType` como PTT (não em `type`, que diz só "mídia"). Transcrição do áudio fica para uma aula posterior.
[00:03:44]

### Exemplo 2: Tempos configurados (timeout e atendimento humano)
`message.timeout` fixo em 10 segundos para juntar mensagens antes de responder (evita responder linha a linha). `message.atendimento` em 720 segundos (15 minutos) de pausa da IA quando o dono manda uma mensagem outcoming.
[00:12:37]

### Exemplo 3: Demonstração vermelho vs verde
O autor copia um campo referenciado corretamente (verde), insere um nó intermediário e mostra o campo virar vermelho quando a referência de origem se perde, depois recorrige apontando o nó certo para voltar a verde.

## 7. Contra-argumentos e nuances

Pontos onde o autor reconhece limites, excecoes ou contradicoes do proprio framework:

- A formatação por prefixo com ponto (`user.` / `message.`) é totalmente opcional, serve só para organização; você pode fazer ou não. [00:07:36]
- Os nomes das variáveis ("Setar Variáveis", origem, etc.) são livres: "pode ser isso, pode ser qualquer outro nome". [00:01:23]
- O campo de tempo pode ser fixo (fixed) ou expressão (expression); com expression funciona também, mas neste caso ele usa valor fixo. [00:12:52]
- Algumas variáveis (Base URL, token) são "mais opcionais" dependendo do fluxo. [00:11:44]

## 8. Aplicacao no nosso contexto

> Esta secao conecta o conhecimento absorvido com o que ja existe no vault (BaseX, bot de WhatsApp para grupos de alunos).

**O que isso muda na nossa operacao:**
O bot BaseX (WhatsApp em grupos de alunos, Evolution API + n8n + Claude, atendendo dúvidas e gestão) deve ter, logo após o webhook da Evolution, um node Set "Setar Variáveis" que normaliza o payload num contrato estável, independente do formato cru da Evolution. Estrutura de variáveis robusta sugerida a partir da aula:

- **origem** — derivar de `isFromMe` para `incoming`/`outcoming`; permite pausar o Claude quando um humano do time BaseX responde no grupo (atendimento humano).
- **grupo (sender do grupo)** — `isGroup` + identificador do grupo (JID). Como o bot opera em grupos, o id do grupo é o roteador principal: separa qual turma/grupo está falando e para onde o fluxo vai.
- **remetente (sender do participante)** — quem enviou dentro do grupo (número do aluno), distinto do JID do grupo. Em grupo, sender do grupo e autor da mensagem são campos diferentes; separe os dois.
- **message.id** — para deduplicar e verificar mensagens já processadas (evita responder duas vezes).
- **message.type via MediaType** — desambiguar áudio (PTT) vs texto vs imagem; roteia áudio de aluno para transcrição antes do Claude.
- **message.timestamp** — base do agrupamento (juntar várias mensagens picadas do aluno antes de mandar ao Claude).
- **message.content** — o texto (em `message.conversation`) ou o placeholder de mídia.
- **token / Base URL da Evolution** — centralizados no Set; se trocar de instância/API, muda num lugar só.
- **timeout / atendimento** — segundos para agrupar mensagens (ex: 10s) e segundos de pausa do bot quando o time humano intervém (ex: 720s).

Boas práticas transportadas: referenciar sempre o nó de origem (evita quebra ao inserir nós), tipar corretamente cada campo, agrupar por prefixo (`grupo.`, `aluno.`, `message.`, `api.`) e manter as variáveis mutáveis (timeouts, token) no fim do Set para edição rápida. Manter um Set de backup para uma segunda API de WhatsApp caso a Evolution caia.

**Acao concreta sugerida:**
- [ ] Adicionar/auditar node Set "Setar Variáveis" no fluxo do bot BaseX logo após o webhook Evolution
- [ ] Padronizar contrato de variáveis: grupo (JID), remetente (aluno), origem, id, type (MediaType), timestamp, content, token, timeout, atendimento
- [ ] Garantir referência ao nó de origem em todos os campos (checagem verde) e tipagem correta
- [ ] Definir timeout de agrupamento e tempo de pausa para atendimento humano no grupo
- [ ] Avaliar node Set de backup para segunda API de WhatsApp
