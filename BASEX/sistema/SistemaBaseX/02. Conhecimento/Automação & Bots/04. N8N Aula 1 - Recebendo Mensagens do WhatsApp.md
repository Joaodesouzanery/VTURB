# Automação e Agentes de IA no N8N: Recebendo mensagens do WhatsApp (Aula 1)

> Primeira aula prática de N8N: como configurar o node Webhook para RECEBER mensagens do WhatsApp via uma API de WhatsApp, entendendo que todo fluxo funciona com chamadas de API (entrada webhook, saída HTTP request).

**Canal:** [Rhavi Criador Digital](https://criador.digital)  · **Duracao:** 00:18:24 · **Publicado:** 2025-03-28 · [Assistir](https://www.youtube.com/watch?v=oEiKLyjBtEQ)

---

## 1. Tese central

Todo fluxo no N8N funciona com chamadas de API: uma entrada (normalmente um Webhook) e uma saída (normalmente um HTTP request), com módulos de transformação de dados no meio. Para construir um chatbot de WhatsApp com IA, o primeiro passo é conectar uma API de WhatsApp (um servidor que faz a ponte com o WhatsApp) ao node Webhook do N8N, configurado em POST, para começar a receber as mensagens. Esta aula cobre só a etapa de recebimento; o tratamento dos dados vem na aula seguinte.

## 2. Frameworks e modelos mentais

> Cada framework recebe nome, explicacao, quando aplicar e citacao verbatim com timestamp.

### 2.1 Entrada e Saída de um Fluxo (tudo é chamada de API)

**O que e:** modelo mental de que qualquer fluxo N8N é uma sequência linear de chamadas de API: uma entrada, transformações no meio e uma saída.

**Como funciona:**
1. Entrada: um Webhook (que é uma chamada de API via webhook) recebe o dado.
2. Meio: módulos de transformação (ex.: OpenAI, que também funciona por chamada de API) tratam o dado.
3. Saída: um HTTP request (também chamada de API) devolve o dado para onde precisa ir (no caso, de volta para o WhatsApp).

**Quando aplicar:** ao desenhar qualquer automação no N8N, para entender por onde o dado entra e por onde sai.

**Quando NAO aplicar:** não é uma limitação; é o modelo base. O autor não aponta contraindicação.

> "Tem a entrada e normalmente a saída é um HTTP request. [...] Um webhook nada mais é que uma chamada de API também via webhook. E tem essa saída que é um HTTP request que também é uma chamada de API. E no meio aqui a gente tem vários módulos de transformação desses dados."
> [00:01:41]

### 2.2 Webhook em POST porque a API ENVIA para o N8N

**O que e:** regra de configuração do método HTTP do node Webhook. Como a API de WhatsApp vai ENVIAR mensagens para o N8N, o webhook precisa esperar por dados, logo o método é POST.

**Como funciona:**
1. A API de WhatsApp é quem dispara a chamada para o N8N.
2. O Webhook do N8N fica esperando receber mensagens, então usa POST.
3. Se em vez de receber você quisesse buscar dados de um banco, aí seria GET.

**Quando aplicar:** sempre que o webhook for o ponto de entrada que recebe eventos de uma API externa.

**Quando NAO aplicar:** para buscar informações de fora (puxar dados de um banco), o método correto seria GET.

> "Porque a API que vai enviar para o N8N, esse Webhook, ele vai estar esperando por mensagens. Por isso ele precisa ser em post. Se a gente estivesse querendo, por exemplo, pegar informações de algum banco de dados, aí seria get."
> [00:08:08]

### 2.3 Testar o fluxo inteiro desde o início (comportamento do N8N)

**O que e:** no N8N o teste sempre parte do node inicial e precisa terminar com sucesso; um módulo lá no final não roda sozinho. Por isso se usa "Pin" para congelar os dados de entrada e não depender do WhatsApp a cada teste.

**Como funciona:**
1. Ao testar, o fluxo começa do início e percorre até o fim.
2. Clicar em "Pin" no node de entrada salva os dados recebidos, para reutilizar em cada teste sem mandar mensagem nova.
3. Cada módulo seguinte só é alcançado testando o fluxo todo.

**Quando aplicar:** durante todo o desenvolvimento incremental do fluxo, para não precisar reenviar mensagens do celular a cada iteração.

**Quando NAO aplicar:** em produção o pin não é usado; ele serve para a fase de teste.

> "Porque no N2N você sempre tem que testar o fluxo todo para chegar no próximo módulo. Ele não funciona assim lá no final, sozinho. Ele sempre tem que começar do início e sempre vai terminar com sucesso no final."
> [00:12:58]

## 4. Heuristicas e regras

Regras-de-bolso, atalhos mentais, principios que o autor enfatiza:

- **Trocar GET para POST no webhook**: erro comum: o webhook vem em GET por padrão e a pessoa esquece de mudar para POST, mas a API precisa ENVIAR para o N8N. [00:13:44]
- **Trocar a URL do webhook pelo seu subdomínio**: o link original fornecido pelo N8N às vezes funciona, muitas vezes não. Dependendo da instalação (ex.: Easy Panel), o host vem errado; troque pelo seu subdomínio real. [00:13:55]
- **Ativar o webhook na API**: dependendo da API você precisa ativar o webhook. Na Evolution: entrar na instância, ir em Eventos > Webhook e colar a URL. [00:14:18]
- **Selecionar Base 64 para mídia**: ativar Base 64 na Evolution faz áudios e imagens virem embutidos, facilitando o tratamento lá na frente. [00:14:53]
- **Selecionar apenas o evento message upsert**: só esse já serve para receber todas as mensagens; outros eventos são opcionais. [00:15:07]
- **Usar Pin para não depender do celular**: congele a mensagem de teste para levar esses dados para frente sem reenviar do WhatsApp. [00:12:43]
- **Renomear o path do webhook**: deixe um nome descritivo (ex.: "aula") para visualizar cada fluxo mais facilmente. [00:08:34]

## 7. Contra-argumentos e nuances

Pontos onde o autor reconhece limites, excecoes ou contradicoes do proprio framework:

- A Avisa API é mais simples e tem menos endpoints (só enviar mensagens, editar mensagens, enviar imagens/áudios/documentos, receber áudio). Tem tudo o que a aula precisa, mas para um projeto mais complexo a Evolution, muito mais robusta, é a indicada. [00:05:22]
- A Evolution permite ignorar grupos nas configurações, mas nem toda API tem essa opção. Quando faltar, dá para resolver com um filtro externo (Hookdeck). [00:16:43]
- Enquanto o webhook escuta, ele recebe TODAS as mensagens o tempo todo, inclusive de todos os grupos dos quais você participa. Isso é o comportamento padrão e pode ser indesejado sem filtro. [00:16:06]
- O link original do webhook fornecido pelo N8N "às vezes funciona, muitas vezes não", dependendo de como o N8N foi instalado. Não é confiável usar direto. [00:13:46]

## 8. Aplicacao no nosso contexto

> Esta secao conecta o conhecimento absorvido com o projeto do bot BaseX (WhatsApp em grupos de alunos, com Evolution API + n8n + Claude, para responder dúvidas e apoiar a gestão).

**O que isso muda na nossa operacao:**
Esta aula é o alicerce técnico exato do bot BaseX. O bot vive em GRUPOS de alunos, e o vídeo mostra que o node Webhook em POST, ativado na Evolution via Eventos > Webhook com o evento message upsert, é o que faz o n8n começar a receber as mensagens dos grupos. Dois pontos são decisivos para o nosso caso:
1. O webhook escuta todas as mensagens de todos os grupos por padrão. Para o bot BaseX, que deve atuar só nos grupos de alunos certos, isso obriga uma camada de filtragem. A Evolution já traz "ignorar grupos"; para o inverso (atuar SÓ em grupos específicos por código de grupo), o Hookdeck é o filtro intermediário citado, que encaminha ao n8n apenas as mensagens dos grupos permitidos. Isso reduz ruído e custo de execução.
2. Ativar Base 64 na Evolution faz áudios e imagens dos alunos chegarem embutidos, o que facilita depois passar para o Claude tratar (dúvidas por áudio ou print são comuns em grupo).
A saída (HTTP request de volta ao WhatsApp) não é coberta aqui, mas o modelo entrada/transformação/saída já mapeia onde o Claude entra (módulo de transformação) e por onde a resposta volta.

**Acao concreta sugerida:**
- [ ] Confirmar que o webhook do fluxo BaseX está em POST e apontando para o subdomínio real do n8n (não o link cru gerado nem host de painel).
- [ ] Na Evolution, ativar o evento message upsert e o Base 64 na instância dos grupos de alunos.
- [ ] Avaliar Hookdeck como filtro para restringir a atuação do bot apenas aos códigos de grupo dos alunos (whitelist), evitando processar todo grupo.
- [ ] Usar Pin durante o desenvolvimento do fluxo BaseX para testar sem depender de mensagens reais nos grupos.
