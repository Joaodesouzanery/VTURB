# 75. Analisar Operacao

> Lê o .xlsx que você exportou do Gerenciador de Anúncios, monta o briefing dos números, aponta o gargalo com a causa provável e propõe as ações em ordem de prioridade, parando a cada fase para você validar.

## O que você precisa ter antes

- Node 20 ou mais novo.
- A biblioteca `xlsx` instalada dentro do motor. Uma linha, uma vez só: `cd "_engine/analisar-operacao" && npm install`. Sem ela o pre-flight bloqueia.
- A pasta `02. Conhecimento/Operação & Performance`, com o arquivo `01. Catálogo de Ações e Placar de ROI.md` dentro. Já vem pronta no SistemaBaseX, com os marcadores que o placar usa para espelhar a tabela. Só entra na sua lista se você renomear ou apagar a pasta: aí o pre-flight bloqueia até ela voltar com o nome exato.
- O export .xlsx do dia, tirado do Gerenciador de Anúncios do Meta. Isso pede conta de anúncios com histórico de gasto.
- Colunas exigidas nesse export, porque o preset padrão do Gerenciador não traz as de conversão: valor usado, impressões, alcance, frequência, cliques no link, CTR de cliques no link, CPM, compras, valor de conversão de compras, ROAS de compras e custo por compra. Adicione as que faltarem em Colunas, Personalizar colunas, antes de exportar. Coluna que não vem no arquivo vira KPI vazio no briefing, sem erro nenhum na tela. A taxa de conversão não existe como coluna: ela sai de compras dividido por cliques no link.
- Opcional, um segundo .xlsx de um período maior, para comparar o dia contra a tendência.
- Se a conversa chegar em margem e CPA alvo, o custo do produto é perguntado em dólar, com o frete já incluso nesse número.

## O que ela faz

Ela funciona como um analista que volta toda semana na mesma loja: lê os números, compara com o que já viu, aponta onde o dinheiro está vazando e propõe o que fazer, nessa ordem.

O motor cuida de três coisas concretas:

| Peça | O que ela faz de fato |
|---|---|
| `parse-xlsx.mjs` | Normaliza os cabeçalhos do export do Meta para nomes canônicos usando o `header-map.json`, que aceita português e inglês |
| `score-engine.mjs` | Mantém um placar de ações em `data/placar.json`: ação que subiu o ROI ganha pontos, ação que derrubou perde |
| `history-rotate.mjs` | Grava as métricas do dia num histórico de 28 dias por loja, com backup antes de sobrescrever |

O diagnóstico em si, o ranqueamento das causas e as soluções são raciocínio, não script. O `breakpoints.json` entra como régua: CTR de link mínimo de 1%, frequência máxima de 2,5 em 7 dias, conversão mínima de 1,5%, CPA alvo em 30% do ticket, e uma guarda estatística de 1000 impressões, 50 cliques e pelo menos um CPA alvo de gasto antes de qualquer decisão.

A skill para ao fim de cada fase. Ela não encadeia sozinha.

## Como usar

Todos os comandos rodam de dentro do motor:

```bash
cd "_engine/analisar-operacao"
```

**Fase 0, pre-flight.** Obrigatório, sempre:

```bash
node preflight.mjs
```

Saída 0 libera. Qualquer bloqueio vem com a correção escrita ao lado.

**Fase 1, briefing.** Normalizar as planilhas:

```bash
node parse-xlsx.mjs "caminho/do/dia.xlsx" --out "_tmp_dia.json"
node parse-xlsx.mjs "caminho/do/periodo.xlsx" --out "_tmp_periodo.json"
```

O parse escreve na tela quantas colunas foram mapeadas e quais ficaram de fora. Com o JSON pronto, a skill apresenta faturamento, ROAS, CPA, ticket médio, taxa de conversão, gasto, frequência, CPM e CTR, com a comparação do dia contra o período. **Ela para aqui** e pergunta se pode seguir.

**Fase 2, gargalos.** Cada KPI fora da régua vira um gargalo, e cada gargalo recebe as causas prováveis separadas por dimensão: loja, criativo, preço e oferta, funil, rastreamento. **Ela para aqui** com os gargalos ordenados por severidade.

**Fase 3, soluções.** Ler o que o placar já aprendeu:

```bash
node score-engine.mjs list
```

As ações com mais pontos entram primeiro na lista de recomendação. Ação sem histórico é marcada como hipótese, não é promovida. Quando o gargalo puder ser atacado por dois caminhos diferentes, por exemplo trocar o criativo ou mexer na página de produto, a skill pergunta qual você quer atacar antes de montar o plano. **Ela para aqui** com o plano de ação.

**Fase 4, quando não há gargalo.** Se nada estourou a régua, ela sugere só otimizações acima dos break points, respeitando a guarda estatística, e lê o efeito das ações que você já executou e ainda não tinham sido analisadas.

**Fase 5, gravar.** Conferir antes de escrever:

```bash
node history-rotate.mjs --loja "Minha Loja" --metrics "_tmp_metrics.json" --dry-run
```

Gravar:

```bash
node history-rotate.mjs --loja "Minha Loja" --metrics "_tmp_metrics.json"
```

O `_tmp_metrics.json` é um objeto simples com `faturamento`, `roas`, `cpa`, `conversao` e `gasto`. Nenhum script escreve esse arquivo: ele é montado à mão com os números que a Fase 1 apurou, e os nomes das chaves são exatamente esses, `conversao` sem acento. Para gravar em outra pasta que não a padrão, use `--dir "Nome da pasta"`.

Quando uma ação já executada tiver resultado conhecido, registrar no placar:

```bash
node score-engine.mjs record --action "reduzir CPA alvo" --context "Minha Loja" --roi-before 1.4 --roi-after 1.9
```

Para regenerar só o espelho em texto do placar:

```bash
node score-engine.mjs render
```

Se algo entrou errado no histórico:

```bash
node history-rotate.mjs --loja "Minha Loja" --rollback
```

Ao final, apagar os arquivos `_tmp_*.json`.

## O que ela devolve

Um relatório em fases, uma de cada vez, com validação entre elas:

```
=== Análise de Operação, Minha Loja, 2026-09-03 ===

FASE 1  Briefing
  Faturamento, ROAS, CPA, ticket, conversão, gasto. Dia contra período, com a tendência de cada um.

FASE 2  Gargalos
  [alta] Conversão em 0,7%, abaixo de 1,5%
         causas: página de produto, oferta, rastreamento

FASE 3  Soluções priorizadas
  1. [+3 pontos] Ação com histórico bom no placar
  2. [sem histórico, hipótese] Ação nova

FASE 4  Se não houve gargalo: otimizações acima dos break points

FASE 5  Gravado
  Minhas Lojas/Minha Loja/_Operação/historico-4-semanas.md, backup em .bak
```

O histórico fica em `Minhas Lojas/{loja}/_Operação/historico-4-semanas.md`, contado a partir da raiz do SistemaBaseX, com no máximo 28 dias de linhas. O placar fica em `_engine/analisar-operacao/data/placar.json`.

## Onde erra

**O pre-flight falha na primeira vez.** Numa instalação nova ele acusa `Lib xlsx instalada` e termina com `1 bloqueio(s)`, porque a lib não vem instalada. Resolve com `npm install` dentro do motor. Se aparecer também `Pasta de catálogo/placar global`, a pasta `02. Conhecimento/Operação & Performance` foi renomeada ou apagada. Rodar as fases seguintes com o pre-flight vermelho quebra o parse no meio.

**O histórico não vai para onde você acha que vai.** O `history-rotate.mjs` não conhece nenhuma flag de tipo de loja. Se você passar algo como `--type cliente`, ele ignora em silêncio e grava em `Minhas Lojas/{loja}/_Operação/`. Como perceber: você procura o arquivo na pasta que criou para a loja e ele não está lá. A flag que existe é `--dir`.

**O placar nasce vazio e continua vazio por semanas.** Ele só ganha entrada quando alguém roda `record` com o ROI antes e o ROI depois de uma ação já executada. Enquanto isso, `list` responde `(placar vazio)` e a Fase 3 não tem como ordenar por histórico: tudo cai em hipótese. Inventar pontuação para preencher a coluna é o erro mais fácil de cometer aqui.

**O `record` grava e o espelho falha na mesma linha.** Se o catálogo `.md` não existir, ou existir sem os marcadores `PLACAR:START` e `PLACAR:END`, o script escreve `nada foi espelhado` e mesmo assim o `placar.json` já foi atualizado. Como perceber: a saída traz `Placar atualizado.` e a mensagem de catálogo não encontrado juntas. O dado está salvo, só a tabela legível não saiu.

**Coluna não mapeada some sem quebrar nada.** Se o cabeçalho de compras ou de ROAS não bater com nenhum sinônimo do `header-map.json`, o KPI simplesmente fica vazio no briefing e o diagnóstico segue em cima de um número que não existe. Como perceber: a linha `[parse] N linhas | X colunas mapeadas | Y não mapeadas`, com a lista das que ficaram de fora. Acrescente o sinônimo no `header-map.json` e rode o parse de novo.

**Diagnosticar a loja a partir de uma planilha de anúncios.** O motor lê o export do Meta e nada mais: ele não abre a sua loja, não lê o pixel, não olha o comportamento do visitante. Quando a Fase 2 aponta rastreamento ou página de produto como causa, isso é hipótese para confirmar com uma auditoria de pixel ou de comportamento, e o relatório precisa dizer isso com essas palavras.

**Decidir com um dia de dados.** Com poucas compras no dia, o ROAS balança sozinho e você mata um criativo que estava certo. A guarda estatística do `breakpoints.json` existe para isso: abaixo de 1000 impressões, 50 cliques e um CPA alvo de gasto, não há decisão a tomar, só ruído a observar.

**Chave errada no `_tmp_metrics.json` vira traço.** O script só conhece `faturamento`, `roas`, `cpa`, `conversao` e `gasto`. `conversão` com acento, ou qualquer outro nome, é ignorada e a coluna entra com `-`. Como perceber: a linha do `--dry-run` sai com traço onde devia ter número, e o script imprime `AVISO: chave(s) ignorada(s)` logo acima. Caminho de arquivo errado é diferente: aí o script bloqueia, em vez de gravar um dia em branco.

**O backup guarda um passo só.** O `.bak` é sobrescrito a cada gravação. Se você gravou uma métrica errada e rodou de novo antes de perceber, o `--rollback` restaura o erro, não o estado bom. Confira o `--dry-run` antes de gravar, que ele imprime exatamente a linha que vai entrar.
