# 111. Auditar Pixel Meta

> Percorre o funil da sua loja num navegador, captura cada evento do pixel com os parâmetros e diz, evento por evento, o que está chegando no Meta e o que não está.

## O que você precisa ter antes

- Node 20 ou mais novo, para rodar o motor.
- O domínio público da loja no ar e sem página de senha. O pre-flight faz um acesso com 20 segundos de limite e desiste depois disso.
- Um MCP de navegador conectado: `chrome-devtools`, que exige o Chrome aberto com `--remote-debugging-port=9222`, ou o Playwright MCP. Sem navegador a auditoria não acontece, porque HTML parado não prova disparo de evento.
- Opcional, o ID do pixel que você espera encontrar. Com ele a skill confere se a loja aponta para o dataset certo.
- Opcional, acesso de administrador ao Gerenciador de Eventos do Meta. Sem ele o veredito cobre só o lado do site, e isso fica escrito no relatório.

## O que ela faz

A skill trabalha em duas metades, e é honesto saber qual é qual.

**A metade do motor.** O `preflight.mjs` faz um acesso ao HTML inicial da loja e responde cinco coisas: a loja responde, é Shopify, quais IDs de pixel aparecem no código da página, existe banner de consentimento e existe indício de rastreamento pelo servidor. Isso é diagnóstico de partida, não veredito.

**A metade do navegador.** Tudo que vale de verdade acontece aqui:

| Verificação | O que ela procura |
|---|---|
| Pixel presente | Requisições para `facebook.com/tr` no log de rede. `fbq` definido e `fbq.getState()` entram como confirmação secundária, e ficam ausentes quando o pixel roda no sandbox de Web Pixels, o que é o normal na Shopify de hoje |
| Quantos pixels | Mais de um pixel na mesma página significa público contaminado, quase sempre sobra de instalação antiga |
| Pixel certo | Compara o ID encontrado com o que você informou |
| Eventos por etapa | Percorre home, página de produto, carrinho e checkout, capturando o que dispara em cada uma |
| Parâmetros | `value`, `currency`, `content_ids` e `content_type` nos eventos que precisam deles |
| Duplicação | Mesmo evento disparado duas vezes sem `eventID`, o que acontece quando o app e o tema instalam o pixel ao mesmo tempo |
| Consentimento | Se o evento só dispara depois do aceite, e quanto se perde antes disso |
| Velocidade | Quanto tempo o pixel leva para carregar, porque pixel lento perde quem sai rápido |

A skill é somente leitura. Ela navega, mede e lê. Não altera o tema, não instala app, não mexe em dataset. A instrumentação vive só na aba aberta e some quando você fecha.

## Como usar

**Passo 1, pre-flight.** A partir da raiz do SistemaBaseX:

```bash
cd "_engine/auditar-pixel"
node preflight.mjs minhaloja.com
```

Com o ID esperado, que é opcional:

```bash
node preflight.mjs minhaloja.com 1234567890123456
```

Saída 0 significa liberado. Ele escreve na tela a plataforma, os pixels achados no HTML, se há banner de consentimento e se há indício de rastreamento pelo servidor.

**Passo 2, abrir a loja no navegador e ler a rede.** É aqui que está a prova. Com o log de rede ligado, listar as requisições, filtrar `facebook.com/tr` e ler a query string de cada chamada: `ev` diz o evento, `id` diz o pixel, `eid` diz se há deduplicação e `cd[...]` traz os parâmetros. Na Shopify de hoje o pixel roda dentro do sandbox de Web Pixels, e a requisição aparece no log normalmente mesmo quando `fbq` não existe na página. Requisição saindo é pixel vivo.

**Passo 3, conferir o `fbq` no frame principal.** Leitura secundária, que serve para saber se, além do sandbox, existe um pixel instalado direto no tema:

```js
window.fbq && fbq.getState
  ? fbq.getState().pixels.map(p => ({ id: p.id, eventCount: p.eventCount }))
  : null
```

`null` aqui não é pixel ausente, é o resultado esperado quando o pixel vive só no sandbox. Se vier lista, compare os IDs com os que saíram na rede: o mesmo ID dos dois lados é candidato a disparo duplicado.

**Passo 4, instrumentar o `fbq`,** quando ele existir no frame principal. Envolver a função original guardando cada chamada em `window.__auditoria_pixel`, preservando `queue`, `callMethod` e `getState` para não quebrar o pixel da loja. A partir daí todo `fbq('track', ...)` fica registrado com os parâmetros. Com `fbq` indefinido, pule este passo: a rede do Passo 2 cobre o funil inteiro sozinha.

**Passo 5, percorrer o funil** na mesma aba: home, página de produto, adicionar ao carrinho, abrir o checkout. A cada etapa, ler as requisições novas para `facebook.com/tr` e, se houve instrumentação, também o que ela capturou.

**Passo 6, se a loja tem banner de consentimento,** repetir os passos 2 a 5 sem aceitar os cookies. São dois relatórios, e a diferença entre eles é o tamanho do buraco.

**Passo 7, se você tem acesso ao Gerenciador de Eventos,** comparar o que o navegador disparou com o que o Meta diz ter recebido nos últimos 7 dias. É esse cruzamento que separa "a loja não dispara" de "a loja dispara e o Meta não recebe".

## O que ela devolve

Um relatório curto, com o achado e o conserto lado a lado:

```
PIXEL          1234567890123456 · único · confere com o esperado
HOME           PageView ok
PRODUTO        PageView ok   ViewContent ok (content_ids, value, currency)
CARRINHO       AddToCart ok (value, currency)
CHECKOUT       InitiateCheckout FALHOU, não disparou

VEREDITO       Rastreamento incompleto no checkout. Corrija antes de subir campanha.
```

Quando não houve acesso ao Meta, o veredito diz na primeira linha que cobre só o lado do site.

Quando você não informou o ID esperado, a linha do pixel sai na variante honesta, sem fingir conferência: `PIXEL 1234567890123456 · único · ID esperado não informado, não dá para dizer se é o dataset certo`.

A tabela de conserto que acompanha:

| Achado | O que significa | Conserto |
|---|---|---|
| Nenhuma requisição para `facebook.com/tr` em nenhuma etapa | Não instalado, ou bloqueado pelo consentimento | Instalar pelo app do Meta e conferir o tema |
| Dois ou mais pixels | Público contaminado entre operações | Remover o pixel antigo do tema ou do app |
| Pixel diferente do esperado | A loja aponta para o dataset errado | Corrigir no app e no tema |
| ViewContent sem `content_ids` | Catálogo e remarketing dinâmico não funcionam | Corrigir o mapeamento no app |
| Purchase sem `value` ou `currency` | O Meta não consegue calcular ROAS | Corrigir o evento no tema |
| Mesmo evento duas vezes sem `eventID` | App e tema disparando juntos, sem deduplicação | Manter um dos dois, ou ativar a deduplicação por `eventID` |
| Evento só dispara após aceitar cookies | Você perde tudo de quem não aceita | No app de consentimento, liberar o pixel como essencial ou disparar assim que houver aceite |
| A loja dispara e o Meta não recebe | Bloqueio do navegador do visitante | Ativar envio pelo servidor com a Conversions API |

## Onde erra

**Você roda só o pre-flight e acha que auditou.** O motor lê o HTML inicial e nada mais. Como perceber: você tem a saída do pre-flight e nenhuma linha de CARRINHO ou CHECKOUT. Presença no código não é disparo de evento. Sem navegador conectado, pare e resolva o navegador.

**`fbq` indefinido não é pixel ausente.** Na Shopify de hoje o pixel instalado pelo app do Meta roda dentro do sandbox de Web Pixels, e `window.fbq` no frame principal vem `undefined` numa loja perfeitamente instalada. Concluir "não instalado" aí é o veredito mais caro da skill: manda refazer uma instalação que está certa. Como perceber: `web-pixels-manager` aparece no HTML, `fbq` não aparece em lugar nenhum e mesmo assim saem requisições para `facebook.com/tr` na rede.

**O primeiro PageView já passou quando a instrumentação entra.** Se você contar só o que foi capturado, vai marcar a home como sem PageView numa loja saudável. Como perceber: `fbq.getState()` mostra `eventCount` maior que zero e a lista capturada está vazia. Use o `eventCount` para a primeira página e a captura da navegação seguinte em diante.

**Loja com Conversions API pelo servidor pode não disparar nada no navegador e estar certa.** Concluir "sem pixel" aí é falso negativo. O pre-flight avisa quando encontra indício de server-side, e nesse caso o veredito só fecha com o lado do Meta.

**Auditar só depois de aceitar os cookies.** O relatório sai limpo e a loja continua perdendo os visitantes que fecham o banner. Como perceber: você rodou uma vez só numa loja onde o pre-flight anunciou banner de consentimento.

**Rodar contra a loja com página de senha ligada.** O acesso devolve o HTML da tela de senha, sem pixel nenhum, e o diagnóstico sai "sem pixel" numa loja que tem pixel. Como perceber: o pre-flight diz que é Shopify, não acha pixel algum, e a home pede senha no navegador.

**Dar InitiateCheckout como falho porque a captura veio vazia.** A instrumentação do Passo 4 vive na aba e no documento atual, e não atravessa a ida para `/checkouts/...`, que é documento novo e roda o pixel em sandbox. Como perceber: a lista capturada fica vazia no checkout enquanto a rede mostra a requisição com `ev=InitiateCheckout`. Só a rede prova esse evento, captura vazia ali não é falha.

**Dar Purchase como aprovado.** A skill não compra nada. Purchase só pode ser avaliado pela configuração e pelo histórico do dataset, e é isso que o relatório precisa dizer, em vez de um sinal verde que ninguém testou.

**Confiar no ID que aparece no HTML.** App que injeta o pixel depois faz o ID certo não aparecer no código inicial. O pre-flight já avisa que "só o navegador conclui", e essa confirmação não é opcional.
