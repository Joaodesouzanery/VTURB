# Agente SDR Premium (Template Grátis) Fluxo Completo N8N para WhatsApp

> Walkthrough de instalacao de um fluxo N8N pronto de agente SDR para WhatsApp, o mesmo que o autor usa em clientes high-ticket. Vale absorver porque a arquitetura (webhook, normalizacao, debounce, memoria, RAG, roteamento multiagente, split de mensagens e follow-up) e quase identica ao que o bot BaseX de grupos de alunos precisa.

**Canal:** [Rhavi Criador Digital](https://criador.digital)  · **Duracao:** 00:54:46 · **Publicado:** 2025-06-02 · [Assistir](https://www.youtube.com/watch?v=4fMydexLFL0)

## 1. Tese central

Da para montar um agente SDR de WhatsApp de nivel profissional (usado em vendas de produtos que "valem milhoes", exemplo dado: apartamento de um milhao de reais) importando um unico JSON no N8N e configurando credenciais, sem escrever codigo do zero. O diferencial "Premium" esta no prompt e nas ferramentas acopladas ao fluxo: normalizacao de dados, memoria persistente, RAG sobre documentos, roteamento por modo de agente, split de mensagens humanizado e follow-up automatico com perfil do usuario. A licao operacional dominante e que erros quase nunca sao da IA e sim de configuracao (credencial errada, virgula, espaco), entao atencao cirurgica em cada node.

## 2. Frameworks e modelos mentais

> Cada bloco recebe funcao, posicao no fluxo e citacao verbatim com timestamp.

### 2.1 Normalizacao via "Sete Variáveis" (Set node)

**O que e:** um node Set logo apos o webhook que transforma os dados crus da API em variaveis padronizadas que o resto do fluxo referencia.

**Como funciona:**
1. Extrai do webhook: username, numero de telefone do usuario, quem enviou, origem (grupo ou nao), ID da mensagem, tipo de mensagem, tempo da mensagem, conteudo (texto, imagem ou audio), token da API.
2. Define parametros de operacao: tempo de atendimento (720 segundos = 15 min de pausa apos intervencao humana) e a base URL da Avisa API.
3. Todo o resto do fluxo puxa dessas variaveis, nunca do webhook cru.

**Quando aplicar:** sempre que quiser trocar de webhook ou de API sem quebrar o fluxo inteiro. Muda so a origem, as variaveis continuam iguais.

**Quando NAO aplicar:** nao ha contraindicacao no video. E tratado como camada obrigatoria.

> "Isso aqui e a alma do agente, e o sete variaveis."
> — [00:22:50]

> "Voce nao esta pegando as informacoes que vem no webhook de forma crua. Voce esta normalizando esses dados, ou seja, voce esta organizando."
> — [00:08:00]

### 2.2 Debounce de mensagens picotadas (Redis + Wait)

**O que e:** mecanismo que agrupa varias mensagens curtas enviadas em sequencia numa unica entrada antes de acionar o agente.

**Como funciona:**
1. Cada mensagem entra num buffer no Redis (nodes push, get, delete).
2. Um node Wait segura o fluxo por N segundos (config: 6s no teste, recomendado 6 a 15s, ideal 10s).
3. O tempo esta em DOIS lugares que precisam bater: o node Wait e um numero dentro de uma formula. So o numero pode ser trocado, a formula nao se mexe.
4. Se passar o tempo sem nova mensagem, junta tudo e segue.

**Quando aplicar:** sempre em WhatsApp, onde o usuario manda "oi", "tudo bem", "posso falar" em mensagens separadas.

**Quando NAO aplicar:** a formula so vale para a Avisa API. Com outra API a formula muda.

> "Se a gente nao tiver essa parte aqui, o agente de IA vai responder a cada mensagem separadamente, e a conversa fica muito ruim."
> — [00:19:39]

### 2.3 Controle de atendimento e pausa manual (palavras-chave + coluna agente)

**O que e:** sistema para o dono do WhatsApp interromper a IA numa conversa especifica, por tempo ou de forma permanente.

**Como funciona:**
1. Se a mensagem vem do dono do WhatsApp e contem a palavra-chave de desligar (exemplo no template: "Opa, Jonas aqui!"), grava `off` na coluna `agente` da tabela `contatos_agente`.
2. Palavra-chave de religar (exemplo: "Maravilha até mais!") volta o agente. As frases precisam ser exatas, com acento e exclamacao.
3. Se nao ha palavra-chave, o fluxo apenas pausa a IA por 720s (15 min) via bloco "sete atendimento" e depois retoma.

**Quando aplicar:** cliente pede para falar com humano, ou numero que nao deve receber IA.

> "Quando eu interrompo a IA, eu quero que ela pare de responder por 15 minutos, e depois ela vai voltar a responder normalmente, se o usuario continuar conversando."
> — [00:09:14]

### 2.4 Roteamento multiagente (Switch de modos)

**O que e:** um Switch que direciona a conversa para diferentes agentes conforme o modo salvo no banco.

**Como funciona:**
1. Le o modo do usuario no Supabase. Se `off`, nao responde.
2. Modo padrao = `recepcionista`. O video roda so com um agente, mas o Switch ja esta pronto para receber `especialista`, `secretária` (agendamento), etc.
3. Novos agentes sao adicionados como novas opcoes no Switch.

**Quando aplicar:** quando um unico agente nao cobre todas as funcoes (recepcao vs agendamento vs especialista).

> "Aqui a gente esta fazendo com um agente so, mas aqui ja esta pronto para receber varios agentes."
> — [00:23:15]

### 2.5 Split de mensagens humanizado (Parser Chain + Output Parser + Loop)

**O que e:** divisao da resposta unica do agente em 1 a 4 mensagens para nao mandar textao no WhatsApp.

**Como funciona:**
1. A resposta do agente entra numa Chain (Parser Chain, recomendada por um aluno) com system prompt: "analise se essa mensagem precisa ser separada, prefira 2 split message, mas pode ser de 1 a 4, de forma humanizada".
2. Um Output Parser forca o formato: campo obrigatorio `messages` (array). Isso garante que o split sempre sai certo.
3. Um Loop percorre cada mensagem: envia para a Avisa API, ativa digitando, espera um pouco, envia a proxima, ate `done`.

> "A gente coloca um output parser, para ter certeza absoluta que ele vai sair no formato correto. A gente quer dividir tudo que esta output.messages."
> — [00:29:46]

### 2.6 Follow-up com perfil do usuario (reengajamento + resumo)

**O que e:** agente separado que reativa conversas paradas e mantem um perfil resumido do lead.

**Como funciona:**
1. Cada mensagem do usuario atualiza a data do follow-up (empurra +tempo). Se nao existe follow-up, cria; se existe, faz update.
2. Quando o usuario para por X tempo (15 min, 1h, o que definir), o agente de follow-up dispara para reengajar.
3. O agente de follow-up NAO tem memoria propria: recebe as ultimas 20 mensagens daquele numero. Um code node inverte a ordem (chegavam de tras para frente) e junta os 20 itens numa unica mensagem.
4. Compartilha a mesma documentacao/RAG do agente principal.
5. Cria/atualiza `user_profile` na tabela `contatos_agente`, somando o resumo anterior com as conversas recentes.
6. Precisa colar o token da API manualmente neste ramo, porque aqui ele nao puxa do webhook.

> "O follow-up e quando o usuario para de responder durante 15 minutos, 10 minutos, o tempo que voce definir. Ai a gente manda uma mensagem para reativar aquela conversa."
> — [00:09:59]

> "Ele vai ler as 20 mensagens, mas vai ler as mensagens anteriores tambem... e ai ele vai criar um novo resumo, somando o resumo anterior e as conversas recentes."
> — [00:34:33]

## 4. Heuristicas e regras

- **Cada virgula conta** — uma virgula, um espaco a mais ou uma besteirinha faz tudo parar de funcionar, e o sintoma parece ser "a IA nao responde" quando na verdade e config errada do N8N. [00:21:25]
- **Selecione a credencial correta em CADA node** — o proprio autor cometeu o erro (Supabase errado no Create Follow Up) e o fluxo criava follow-ups infinitos na conta errada. Verificar node por node. [00:38:56]
- **A maioria dos erros nao e da IA** — "muitas vezes tem problemas de instalacoes, e outras vezes tem problema de API mesmo". Se o fluxo responde mas trava, procure config. [00:22:00]
- **Nao mexa na formula do debounce** — so troque o numero de segundos; a formula so vale para a Avisa API. [00:20:08]
- **Avise as capacidades e limites da IA no prompt** — se nao existir tool para uma acao, a IA vai prometer e nao cumprir ("vou anotar seu nome para te chamar de volta" sem tool = mentira). [00:52:32 / 00:51:06]
- **Sempre force a ferramenta de banco de dados** — para o agente nao "tirar coisa da cabeca dele" (alucinacao). [00:50:03]
- **Deixe o fluxo em ativo (nao teste) para producao** — em modo teste/editor aparecem bugs; se der muito erro, feche a aba e reabra. [00:39:55]
- **Coloque Execution Data no inicio E no fim** — se aparece so o dado do inicio, o erro esta depois dele. Debug por eliminacao. [00:32:00]
- **Deletar atendimento facilita teste** — apaga o registro so do seu numero para repetir do zero. [00:13:04]
- **Prefira Avisa API a Evolution para estabilidade** — "se a Evolution cair, voce e responsavel de consertar. Se a Avisa API cair, os desenvolvedores da Avisa API que vao consertar". [00:22:10]

## 6. Exemplos praticos mencionados

### Exemplo 1: Bug do follow-up infinito
Durante o teste ao vivo, a execucao durou 53 segundos (o normal seria 28 a 30s). O node "Create Follow Up" estava com a credencial "Super Base Account" ao inves de "Academia Super Base". Resultado: criava follow-ups infinitos na conta errada do Supabase enquanto o fluxo ja respondia normalmente no WhatsApp. Correcao: trocar a credencial correta nos nodes de follow-up.
[00:38:24]

### Exemplo 2: Teste de memoria em 4 mensagens picotadas
O autor mandou "meu nome e Rhavi", depois perguntou "qual" / "e" / "meu" / "nome" em quatro mensagens separadas. O debounce juntou as quatro, o agente respondeu "seu nome e Rhavi", confirmando que a memoria (Postgres `n8n_chat_histories`) e o split estavam funcionando. Verificacao alternativa: abrir o `pgweb` no EasyPanel e inspecionar a tabela de historico.
[00:41:14]

### Exemplo 3: Ferramenta "salva contato" como subfluxo
A tool envia numero fixo (o do contato) e deixa a IA decidir nome, e-mail, localizacao, interesse e resumo. Abre um subfluxo que faz get do contato, se existe segue para `true` e da update em `contatos_agente` com os campos preenchidos pela IA, retornando "contato salvo com sucesso" para a IA continuar a conversa. Novos campos sao adicionados na definicao do subfluxo, nao no node do agente.

- O video foca em COMO configurar, nao em COMO funciona a fundo. O autor repete que a explicacao detalhada de cada node fica para as aulas pagas da Academia. Entao a nota cobre a arquitetura, mas a logica interna de alguns nodes fica em aberto. [00:06:51]
- O prompt do agente entregue e generico ("viajando na maionese" se nao for customizado). O template funciona plugado, mas o valor real depende de reescrever o prompt para o negocio. [00:24:31]
- A integracao com Google Drive exige dominio proprio; o dominio automatico do EasyPanel "muito provavelmente nao vai funcionar" para o OAuth do Google. [00:35:16]
- O fluxo esta acoplado a Avisa API. Com outra API (Evolution, por exemplo) varias formulas e endpoints mudam. "Isso aqui vai so funcionar com a Avisa API, se nao, vai ter varias coisas que voce vai ter que mudar". [00:54:13]
- As chaves de API do Supabase estavam mudando de lugar no momento da gravacao ("API Keys have moved"), sinal de que a config pode divergir com o tempo. [00:16:07]

## 8. Aplicacao no nosso contexto

> Conecta com o projeto do bot BaseX: WhatsApp em grupos de alunos, stack Evolution API + n8n + Claude, para tirar duvidas e apoiar gestao.

**O que isso muda na nossa operacao:**

Este fluxo SDR e um dos mapas mais proximos do que o bot BaseX precisa. A arquitetura transplantavel quase 1:1:

1. **Camada de normalizacao (Sete Variáveis).** Critica para nos porque o BaseX usa Evolution API (nao Avisa). O node Set que normaliza `username / numero / origem (grupo ou nao) / tipo / conteudo / token` isola a diferenca de API num unico ponto. O campo "origem: grupo ou nao" ja vem no template e e exatamente o que separa mensagem de grupo de aluno vs privado. So a extracao do webhook muda para o payload da Evolution; o resto do fluxo permanece.

2. **Debounce (Redis + Wait).** Em grupo de alunos as mensagens vem picotadas e simultaneas de varias pessoas. O buffer Redis com Wait de 6 a 15s evita o bot responder linha a linha. Ajuste: a chave do buffer deve ser por (grupo + autor), nao so por numero, para nao misturar duvidas de alunos diferentes.

3. **Controle de atendimento + palavras-chave.** O mecanismo de `off` na coluna `agente` e o pause de 720s sao exatamente o "silenciar o bot num grupo" quando um humano da BaseX assume a duvida. Adaptar as frases-gatilho para o time.

4. **Roteamento multiagente (Switch).** Encaixa direto na separacao "duvidas" vs "gestao": um agente FAQ/RAG para duvidas de aluno e um agente de gestao/handoff. O Switch por modo ja esta pronto para isso.

5. **RAG (Vector Store Supabase + Google Drive).** O padrao de alimentar o agente com Google Docs sincronizados diariamente (23:59) e deletar+reinserir os documentos antigos e ideal para a base de conhecimento dos alunos (regras da mentoria, FAQ, materiais). Trocar OpenAI embeddings por pipeline compativel com Claude conforme a stack.

6. **Memoria (Postgres chat histories).** Memoria por conversa ja resolvida. Em grupo, avaliar memoria por thread/aluno.

7. **Split humanizado.** Menos critico em grupo, mas util para respostas longas de duvida.

8. **Follow-up + user profile.** O perfil resumido do usuario em `contatos_agente` (somando resumo anterior + conversas recentes) e ouro para gestao: da para manter um perfil de engajamento por aluno e reengajar alunos sumidos.

9. **Prompt premium estruturado.** O template de system prompt (identidade, objetivo, primeira mensagem, tom, ferramenta obrigatoria de banco, ferramentas adicionais, conhecimento do negocio, fluxo de atendimento, FAQ, regras absolutas, capacidades e limites) e um esqueleto pronto para o prompt do bot BaseX.

**Diferencas a tratar:** API (Evolution no lugar de Avisa muda formulas de debounce, endpoints de typing/envio e a extracao do webhook), LLM (Claude no lugar de GPT-4.1 Mini), e a natureza de grupo (chave de buffer e memoria por autor dentro do grupo).

**Acao concreta sugerida:**
- [ ] Baixar o JSON do template (grupos.criador.digital) e mapear node a node contra o fluxo BaseX atual.
- [ ] Portar o node "Sete Variáveis" para o payload da Evolution API, tratando `origem: grupo` como roteamento.
- [ ] Ajustar chave do buffer Redis para (grupo + autor) e nao so numero.
- [ ] Adotar o esqueleto de system prompt (secao 11 capacidades/limites) para o agente de duvidas do BaseX.
- [ ] Replicar o padrao RAG (Vector Store + sync diario com delete+reinsert) para a base de conhecimento dos alunos.
- [ ] Reusar o padrao user_profile em `contatos_agente` para perfil de engajamento por aluno.
