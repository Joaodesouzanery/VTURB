# Comunicar com Banco de Dados | Curso Básico de N8N (Aula 4)

> Ensina o miolo de qualquer bot: pegar o número de quem mandou mensagem no WhatsApp, procurar no banco, e se não existir, cadastrar. É o passo que dá memória ao fluxo.

**Canal:** [Rhavi Criador Digital](https://criador.digital)  · **Duracao:** 00:18:20 · **Publicado:** 2025-04-02 · [Assistir](https://www.youtube.com/watch?v=u8aU20U5RVo)

## 1. Tese central

No meio de um fluxo n8n de WhatsApp (que já tem início via Webhook e fim via HTTP request), você conecta uma base de dados para saber quem é o usuário. A lógica é sempre a mesma: pesquisar o contato pelo identificador único (o número de telefone), e ramificar com um IF: se existe, segue; se não existe, cria o cadastro e depois junta os dois caminhos de volta num nó Merge para continuar o fluxo.

O autor usa Airtable por ser no-code e amigável a iniciantes, mas deixa claro que o padrão vale para Supabase, BaseRow ou qualquer banco com API (via HTTP Request quando não há módulo pronto).

## 2. Frameworks e modelos mentais

> Cada framework recebe nome, explicacao, quando aplicar e citacao verbatim com timestamp.

### 2.1 Padrão Search → IF → Create → Merge (upsert manual no meio do fluxo)

**O que e:** O esqueleto de qualquer interação de bot com banco de dados. Quatro nós encadeados que transformam "chegou uma mensagem" em "sei quem é essa pessoa e ela está registrada".

**Como funciona:**
1. **Search Records** — pesquisa no banco filtrando pela chave primária (o número de quem mandou a mensagem).
2. **IF (flow)** — verifica se a pesquisa retornou algo. Se sim (true) segue direto; se não (false) desce para o ramo de criação.
3. **Create a Record** — no ramo false, cria o novo contato puxando nome e telefone dos nós anteriores.
4. **Merge** — junta os dois ramos (usuário que já existia + usuário recém-criado) de volta num só caminho para o fluxo continuar (rumo à OpenAI/resposta).

**Quando aplicar:** Toda vez que o bot precisa reconhecer o usuário antes de responder (memória, personalização, histórico).

**Quando NAO aplicar:** Fluxos stateless que respondem igual para todo mundo e não precisam guardar nada.

> "Hoje a gente aprendeu a verificar se um usuário existe no banco de dados, e se ele não existir, a gente pode adicionar informações."
> — [00:17:24]

### 2.2 Regra da Chave Primária

**O que e:** Todo banco de dados tem uma coluna que identifica cada registro de forma única. É por ela que você pesquisa e evita duplicidade.

**Como funciona:**
1. É **imutável** (idealmente não se modifica).
2. É **obrigatoriamente única**.
3. Normalmente é a primeira coluna da tabela.

**Quando aplicar:** Ao escolher por qual campo filtrar/buscar o usuário. No caso de WhatsApp, o telefone vira a chave primária de negócio (porque o e-mail não vem pelo WhatsApp, só o número).

**Quando NAO aplicar:** Nao usar como chave um campo que pode repetir ou mudar (nome, e-mail editável).

> "Todo banco de dados tem uma chave primária, que normalmente é a primeira coluna ali do banco de dados. E ela é duas coisas. Ela é imutável... E, obrigatoriamente, ela é única."
> — [00:06:02]

Nuance do Airtable: a chave primária técnica do Airtable é o **Record ID** (campo escondido, puxável via fórmula `RECORD_ID()`), mas como você não tem o Record ID de cada usuário de antemão, na prática pesquisa-se pelo telefone.

## 3. Conceitos-chave

| Conceito | Definicao | Aplicacao pratica | Timestamp |
|----------|-----------|-------------------|-----------|
| Record = item | No Airtable, "record" é cada linha/item da tabela | Search Records = pesquisar itens; Create a Record = criar item | [00:02:53] |

| Scopes obrigatórios | Permissões que o token precisa ter | data.records:read + data.records:write + schema.bases:read | [00:04:03] |

| Wait/Sleep | Nó de espera (timer) | Segurar 3-5s antes de continuar (ex: mostrar "primeira conexão") | [00:13:22] |

## 4. Heuristicas e regras

Regras-de-bolso, atalhos mentais, principios que o autor enfatiza:

- **Se não tem módulo pronto, use HTTP Request** — qualquer serviço com API na internet conecta via HTTP; hoje a maioria tem API [00:01:57]
- **Telefone é a chave primária no WhatsApp** — o e-mail não chega pelo WhatsApp, só o número, então o número é o identificador único do usuário [00:05:53]
- **Cuidado com duplicidade na chave** — o autor tinha duas contas-teste com o mesmo número; sem verificação de unicidade isso vira problema [00:07:57]
- **Tire o espaço que o Airtable adiciona na fórmula** — ao arrastar a variável do número para dentro das aspas, aparece um espacinho antes que precisa ser removido, senão o filtro não bate [00:07:38]
- **Para "existe ou não", conte o tamanho do objeto, não compare valores** — quando a base está vazia, a fórmula de comparação daria falso e não funcionaria; use `.data.length` [00:14:44]
- **Delete os dados de teste antes de re-testar** — para simular usuário novo, apague o registro de teste da base antes de rodar o fluxo de novo [00:14:24]

## 8. Aplicacao no nosso contexto

> Esta secao conecta o conhecimento absorvido com o bot BaseX (WhatsApp em grupos de alunos; Evolution API + n8n + Claude; atende dúvidas + alimenta gestão).

**Por que banco de dados é CRÍTICO pro bot BaseX:** no nosso caso, o banco não é só cadastro. Ele é a **memória das conversas** dos grupos de alunos, e essa memória é a matéria-prima da análise de gestão. Sem persistir cada mensagem, não há como o Claude analisar engajamento, dúvidas recorrentes, alunos parados ou saúde de turma. A gravação no banco é o que transforma mensagem solta em dado de gestão.

**Como o padrão do vídeo mapeia no nosso fluxo:**

| Etapa do vídeo | Equivalente no bot BaseX |
|---|---|
| Webhook do Avisa API | Webhook da Evolution API (mensagem chega do grupo/aluno) |
| Chave primária = telefone | Chave primária = telefone do aluno (e/ou id do grupo para conversas de grupo) |
| Search Records | Buscar o aluno/grupo no banco (Supabase, não Airtable, por volume) |
| IF `.data.length` | Aluno/conversa já existe? Se não, cria o registro |
| Create a Record | Cadastra aluno novo + abre thread de conversa |
| Merge | Junta os ramos e segue para o Claude gerar resposta/análise |

**Leitura (read):** antes do Claude responder, o fluxo faz Search pelo telefone para recuperar o contexto do aluno (nome, turma, histórico recente da conversa). Esse histórico entra como contexto no prompt do Claude, dando continuidade em vez de responder do zero toda vez.

**Gravação (write):** cada mensagem recebida (e cada resposta do bot) vira um Create/Insert numa tabela de mensagens, com telefone + id do grupo + timestamp + conteúdo + autor. É esse log acumulado que a camada de gestão consome depois para os relatórios.

**Decisão técnica:** para o BaseX use Supabase (o próprio autor diz que fará Supabase numa aula seguinte), não Airtable. Supabase aguenta o volume de mensagens de grupo e permite queries SQL para a análise de gestão, que Airtable não faz bem em escala.

**Acao concreta sugerida:**
- [ ] Modelar no Supabase duas tabelas: `alunos` (chave: telefone) e `mensagens` (fk telefone + id_grupo + timestamp + role + conteudo)
- [ ] Implementar o padrão Search → IF (`.data.length`) → Create → Merge no fluxo n8n do bot, usando telefone como chave
- [ ] Inserir um nó de write de mensagem ANTES e DEPOIS do Claude (grava entrada do aluno e resposta do bot), para o log ser completo
- [ ] Antes do Claude, fazer Search do histórico recente por telefone/grupo e injetar como contexto no prompt
